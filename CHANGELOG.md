## [Unreleased]

### Added
- Project skeleton, tooling (ruff, mypy strict, pytest + coverage ≥ 80%), Linux CI.
- Guard against direct file deletion in code and tests.
- `core.policy`: path blacklist (Windows/Linux/macOS) and default safe zones (`~/.cache`, `~/Downloads`).
- `core.walker`: safe traversal (no symlinks/junctions, pruning of blocked dirs, every skip reported).
- `core.hashing`: streaming BLAKE2b; duplicate candidates via size groups -> prefix hash -> full hash; files changed since scan or during hashing reported as `changed`.
- `core.heuristics` + `core/junk_rules.toml`: junk rules as data (14 default rules: caches, temp, thumbnails, crash dumps, OS metadata) with strict validation.
- `FileEntry.mtime_ns` (int) replaces float `mtime`: exact change detection.
- `storage`: SQLite journal (WAL, foreign keys, synchronous=FULL, busy_timeout), all-or-nothing versioned migrations, `BEGIN IMMEDIATE` transactions with rollback on any exception; schema v1 (`operations`, `items`, STRICT + CHECK).
- `core.open_files` package: `reliable` flag on the checker protocol; Linux backend `ProcFdChecker` (`/proc/*/fd`, matches by `st_dev`/`st_ino`, fails closed); `checker_for_platform()` gives other OSes an unreliable placeholder (decision 0005).
- `BlockReason.APP_DATA`: kresorter's data directory (`$XDG_DATA_HOME/kresorter` or `~/.local/share/kresorter`, `~/Library/Application Support/kresorter`, `%LOCALAPPDATA%\kresorter`) is blacklisted, so the vault and journal never appear in a scan, even when a parent is scanned explicitly; exposed as `PathPolicy.app_data_dir` (decision 0004).
- `quarantine.preflight`: per-item re-validation right before acting (policy -> disk -> duplicate twin -> open files last); 11 refusal reasons incl. parent swapped for a link and hard-linked twin; refuses an unreliable open-file checker.
- `quarantine.vault` and `quarantine.service`: private vault (0700) in the data directory, journal-before-move, same-device `Path.replace` only (`CROSS_DEVICE` refused), atomic batch with rollback that never overwrites, `recover()` that trusts only an exact vault copy (decision 0006). Default data directories stay blocked under custom `XDG_DATA_HOME`/`LOCALAPPDATA`.
- Restore: `QuarantineService.restore()` puts files back with journaled mode/atime/mtime, never overwrites (`CONFLICT`), recreates missing parents, refuses a swapped parent chain, marks a missing or changed vault copy `lost`; items are independent; interrupted restores are reconciled by `recover()` (decision 0007). Journal schema v2: `items.atime_ns`. Duplicate candidates in one batch are refused up front.
- Purge: `QuarantineService.plan_purge()` (read-only plan with `total_bytes` and a one-time token) and `purge(plan)` (same service, unchanged plan, once); deletes only vault copies that still match the journal, never the original path; a changed copy becomes `lost` and is kept; `DELETE_FAILED` keeps the item quarantined; interrupted purges are reconciled by `recover()` (`RecoveryReport.purged`). `quarantine.purge.delete_from_vault` is the single deletion point (vault slots only, `UnsafeDeleteError`); the AST guard now also catches uncalled references and `from os import remove`-style imports, with a pinned one-file allowlist (decision 0008).
- `kresorter quarantine add / list / restore / purge [--yes]`: purge shows its plan and deletes only with `--yes`; every command recovers interrupted operations first (LOST warnings on stderr); exit codes 0/1/2/3 (3 = unsafe to run); the data directory is checked before anything is created and kept 0700 (decision 0009). `kresorter.text` holds the shared size formatting.
- `storage.lock.InstanceLock`: single-instance lock on the data directory (`flock` / `msvcrt.locking`, released by the kernel on crash, lock file 0600 and never deleted); a second `kresorter quarantine` on the same data directory exits with 3 (decision 0009, addendum).
- `analysis.duplicates.decide()`: which copy of a duplicate group stays (not junk -> outside safe zones -> oldest `mtime_ns` -> shallowest -> path order) with the winning `KeepReason`; every other copy becomes a quarantine `Candidate` twinned with the keeper; a group never loses all copies; deterministic (decision 0010, which also fixes the safety levels SAFE / LIKELY_SAFE / REVIEW).
- `analysis.size_age.find_large_and_old()`: large (default >= 500 MiB) and old (unmodified >= 730 days, by `mtime_ns` only; a future `mtime` is never old) files with all their reasons in a fixed order; evidence for `REVIEW` only (decision 0010).
- `analysis.score`: safety levels `SAFE` / `LIKELY_SAFE` / `REVIEW` with a pinned level per `Evidence`; a finding takes its strongest evidence's level, large/old never raise it; every reason is kept strongest first with a user-facing detail; only `SAFE`/`LIKELY_SAFE` are proposed (decision 0010).
- `analysis.report.analyze()`: one read-only pass over a scan (`ScanReport.entries` now keeps every scanned file) that merges junk, duplicate and size/age evidence into one `Finding` per file with its level, reasons and quarantine `Candidate`; a kept duplicate copy is never proposed, even when it is junk; findings ordered by level, size (largest first), path; per-level totals and `proposed_bytes`; absolute paths in findings and reasons alike (decision 0010).
- `kresorter analyze [paths] [--json] [--large MIB] [--older-than DAYS]`: read-only report by safety level (`Safe`, `Likely safe`, `Review (never proposed)`) with every reason under its file, kept duplicate copies marked and never counted, and the proposed total; always looks for duplicates; absolute paths throughout; JSON with findings, duplicate decisions, totals and thresholds (decision 0010). Shared skip and open-file-note rendering moved to `kresorter.text`; `scan` output is unchanged.
- `kresorter quarantine add --from-analysis [paths] --level {safe,likely_safe} [--yes]`: analyzes inside the lock after recovery, shows the plan (exit 1) and moves only with `--yes`; `likely_safe` includes `SAFE`; `REVIEW` findings and kept duplicate copies are never moved; every file is re-checked by preflight at move time; invalid option combinations exit with 2 (decision 0010, addendum).
- `autostart.models`: `AutostartItem` (source, scope, name, command, location, effective `enabled`, `digest` of the raw entry, `shadows` for a user XDG entry replacing a system file) with `disableable` (XDG entries and `HKCU` Run only), `AutostartSkipped`, eight `Source`s (Run and RunOnce apart) and `entry_digest()` (BLAKE2b, 32 hex); decision 0011.
- `autostart.xdg.read_xdg()` and `autostart_dirs()`: XDG autostart entries (`$XDG_CONFIG_HOME/autostart` over `$XDG_CONFIG_DIRS`, first system directory wins), one item per file name with its effective state (`Hidden`, `X-GNOME-Autostart-enabled`); a user entry or `Hidden=true` stub replaces the system entry and names it in `shadows`; `OnlyShowIn`/`NotShowIn` as `notes`; strict, bounded parsing, every unreadable entry skipped with its reason; an unknown effective state is never shown; read-only. `AutostartListing` and `AutostartItem.notes` added (decision 0011, addendum).
- `autostart.systemd.read_systemd_user()` and `systemd_user_dir()`: enabled systemd user units, one item per link in `*.wants/` with `WantedBy=` as a note and `ExecStart` as written; masked units listed as disabled; non-service units listed with their unit file; digest over link target and content; drop-ins, `*.requires/` and `/etc/systemd/user` not read (decision 0011, addendum). `autostart.entries`: bounded, never-blocking entry reading shared by the readers.
- `autostart.registry` (read-only `Registry` protocol, `Hive`, `ValueKind`, `RegValue`, `RegistryError`, length-prefixed `value_digest()`) and `autostart.run_keys.read_run_keys()`: `HKCU` Run/RunOnce always, `HKLM` and its 32-bit view (`WOW6432Node`, flags in `StartupApproved\Run32`) only with `include_machine`; Run state from `StartupApproved` as the Task Manager shows it, unknown states skipped; RunOnce listed as is; tested on a fake registry (decision 0011, addendum).
- `autostart.winregistry.WinRegistry`: the `Registry` protocol on the real `winreg`, imported lazily; keys opened read-only in the 64-bit view; a missing key is `None`, any other failure a `RegistryError`; only `ERROR_NO_MORE_ITEMS` ends an enumeration; keys always closed (decision 0011, addendum).
- `autostart.startup_folders.read_startup_folders()`: Windows startup folders, read-only: the user's (`%APPDATA%`) always, the common one (`%ProgramData%`) only with `include_machine`; one item per file (`desktop.ini` excluded), the command is the file itself, shortcut targets not resolved; state from `Explorer\StartupApproved\StartupFolder` of the same hive, parsed by the shared `registry.approved_state()` (also used by Run); unknown states, sub-folders, oversized files and unreadable folders or flag keys are skipped with a reason; the digest covers file bytes and flag (decision 0011, addendum).
- `autostart.registry.Registry.subkeys()`: names of the keys directly below a key, with the rules of `values()` (missing key `None`, any other failure `RegistryError`); `WinRegistry` reads them with `EnumKey`, read-only in the 64-bit view, ending only on `ERROR_NO_MORE_ITEMS`, the key always closed (decision 0011).
- `autostart.services.read_services()`: Windows services that start automatically, read-only and only with `include_machine`: Win32 services (own or shared process, per-user templates) with `Start=2`, listed as enabled with `ImagePath` unexpanded as the command and the notes `shared process`, `per-user service template`, `delayed start`; drivers, per-user instances, manual and disabled services are not autostart entries; strict parsing, every violation and unreadable key skipped with its reason; the digest covers `Type`, `Start`, `ImagePath` and `DelayedAutostart`; trigger-start services and `svchost` `ServiceDll` are not read yet (decision 0011, addendum).
- `autostart.tasks.read_tasks()` and `tasks_dir()`: Windows scheduled tasks with a boot or logon trigger, read-only and only with `include_machine`, from the XML definitions under `%SystemRoot%\System32\Tasks` (recursive, linked folders not followed); the task path as name, the first action as command (`Exec` unexpanded, `ComHandler` by CLSID), trigger and task state as notes; strict, bounded parsing with any DTD refused, so no entity is expanded; tasks with other triggers only are not listed (decision 0011, addendum).
- `autostart.launchd.read_launchd()` and `launchd_dirs()`: macOS LaunchAgents (`~/Library`, `/Library`) and LaunchDaemons (`/Library`), read-only; one item per `*.plist` (XML or binary) named by `Label`, the argv launchd runs as command, `RunAtLoad`/`KeepAlive` as notes, the state from the file's `Disabled` key with the note `state from the file` (launchd's own overrides are not read); strict, bounded parsing, every malformed property list skipped with its reason; `/System/Library` is not read (decision 0011, addendum).
- `autostart.listing.list_autostart()`: one listing per platform from its readers, in order (Linux XDG and systemd; Windows Run keys, startup folders, services, scheduled tasks; macOS launchd); `AutostartContext` names the environment and directories read and a registry factory called on Windows only, once (decision 0011, addendum).
- `kresorter autostart list [--json] [--include-machine]`: every autostart entry of this system, grouped by source, with state, scope, command, location, shadowed file and notes, then the skips; report only, exit 0; on Windows a note says when machine-wide entries were not read; JSON with platform, consent, every item field and the skips (decision 0011, addendum).
- Journal schema v3: table `autostart_changes` (action, writable source only, listed entry, written location, digest, full bytes before and after up to 64 KiB, vault path, state), migrated from v2 with every quarantine row kept (decision 0011, addendum).
- `autostart.xdg_changes`: the disabled form of an XDG entry, a byte-for-byte copy with `Hidden=true` for the user's own entry (checked by the reader's rules, at most 64 KiB) and a `Hidden=true` stub for a system entry; pure, writes nothing yet (decision 0011, addendum).
- `autostart.changes.XdgChanges.disable`: disables an XDG entry, journaled in `autostart_changes` before the disk is touched; a user's own entry is replaced atomically by its `Hidden=true` copy with the original kept in the private autostart store (same inode), a system entry gets a `Hidden=true` stub created with `O_EXCL` (`/etc` is never written); the entry is checked again as a whole right before acting; refusals (`read_only`, `changed`, `already`, `pending`, `other_device`, `too_large`) change nothing; failures are rolled back without deleting anything (decision 0011, addendum).
- `autostart.changes.XdgChanges.enable`: an own XDG entry disabled by kresorter (by the journal: the last change done there is its disable and the file is that copy) gets its original back, the same inode, atomically, after the original in the store is checked byte for byte; the copy is kept in the store; a `Hidden=true` stub over a system entry is moved to the store; refuses `already`, `foreign` (disabled elsewhere: enabling would edit it), `original_changed` and the refusals of disable; failures are rolled back (decision 0011, addendum).
- `autostart.registry.UserRegistry` and `WinRegistry.set_user_value`: one value written under `HKCU` in the 64-bit view, creating the key if missing; no way to write `HKLM` and no way to delete anything (decision 0011, addendum).
- `autostart.run_changes.RunKeyChanges`: disables and enables an `HKCU` Run value by its `StartupApproved` flag with the Task Manager's bytes (`03` and the FILETIME, `02`), never writing the Run value and never deleting; the value is checked again by its digest right before the write, the change is journaled first, a failure is read back from the registry and journaled `rolled_back` or `failed`; the journal names the flag written exactly (the unnamed one is not a value named `(Default)`); `HKLM` and `RunOnce` are `read_only` (decision 0011, addendum).
- `autostart.run_changes.RunKeyChanges.recover`: closes pending `HKCU` Run changes by the flag in the registry (`done` if written, `rolled_back` if not, `failed` if it is something else), reporting them in `autostart.changes.ChangeRecovery`; it only reads the registry, an unreadable flag leaves the row pending and is raised, and other rows are left alone (decision 0011, addendum).
- `autostart.changes.XdgChanges.recover`: closes pending XDG changes, and failed ones still last at their place, by the disk (`done` only if the store holds what the change kept, `rolled_back` if the entry is as before, `failed` otherwise); nothing is redone or undone and staged copies stay in the store; a partial stub left by a double fault is moved to the store, never deleted; an entry that exists but cannot be read is raised and leaves the row as it is (decision 0011, addendum).
- `storage.pending.has_pending`: one rule for unfinished work; a pending autostart change now also blocks quarantine, restore and purge (and a pending quarantine operation blocks autostart changes) until `recover()` has run; each `recover()` only reconciles its own domain (decision 0011, addendum).
- `kresorter autostart list` shows which entries are `disableable` (a mark in the text, a field in JSON): the source can be written, which does not promise that every action passes (decision 0011, item 56).
- `kresorter autostart recover`: reconciles interrupted autostart changes of this platform (XDG on Linux, `HKCU` Run on Windows) in the shared journal and data directory, under the single-instance lock; an unfinished change that cannot be checked exits with 3 and says what to do. Quarantine `add`, `restore` and `purge` exit with 3 and name this command while an autostart change is unfinished (decision 0011, addendum).
- `kresorter autostart disable|enable ID [--yes]`: changes one XDG entry (Linux) or `HKCU` Run value (Windows) named by any unique beginning of its digest, as `autostart list` now shows it (`id`, 12 characters); without `--yes` it shows what would be written and changes nothing; the change is journaled in the shared journal after the autostart `recover()`; read-only sources, unknown or ambiguous ids and entries already in that state are refused (decision 0011, addendum).
- `kresorter recover`: reconciles the interrupted work of every domain in the shared journal, the quarantine's first (it needs no open-file check, so it also runs on macOS and Windows), then the autostart changes of this platform; `kresorter autostart recover` is its alias (decision 0011, items 124, 126).
- Journal schema v4: `move_batches` (kind `organize` or `undo`, folder, state, times, error) and `moves` (source, destination, the file's device, inode, size and `mtime_ns`, state, and `undoes`, the move an undo reverses), STRICT with `CHECK`s; `operations` is untouched. `Domain.ORGANIZE`: a pending batch is unfinished work that blocks the quarantine and autostart changes until `kresorter recover` (decision 0012, items 24, 32).
- `organize.categories` + `organize/categories.toml`: organize's categories as data (`Images`, `Videos`, `Audio`, `Documents`, `Archives`, `Installers`, in that order), one category per extension, every extension with an example in a test; names are matched folded (NFC, then `casefold`, `organize.names.fold`), the longest extension first (`backup.tar.gz` is an archive); no `Other`, no web pages (decision 0012, items 21-23).
- `organize.platforms`: the pinned table of what keeps organize from moving files on a system (`Blocker`: `no_open_file_check` from the open-file checker; `sharing_violations`, `path_length_limit` on Windows; `cloud_sync` on macOS and Windows), and the refusal that names the system and gives one line per blocker; today only Linux has none (decision 0012, items 37-39).
- `organize.planner.plan(folder, context)`, read-only: the regular files directly in one folder that would move to `<folder>/<Category>/<name>`, by category in table order then by name, and every other entry with its `StayReason` (`not_regular`, `folder_metadata`, `in_progress`, `junk`, `unknown_kind`, `companion`, `program`, `conflict`, `category_blocked`; `missing` is for undo); subdirectories are never entered; names that keep a file in place are compared folded. `organize.folders` refuses a folder as a whole (`FolderRefused`, `FolderReason`): missing, not a directory, a link or below one, blocked by the policy (the data directory included), the home directory or above it, unreadable, a game library or a project (markers as data in `organize/folders.toml`, each with an example in a test), or a cache or temp directory (`JunkClassifier.classify_directory`). `PathPolicy.holds_home` (decision 0012, items 1-18, 20).
- `organize.mover`: `check` takes every planned file again right before the batch, as the quarantine does (policy, open files, the plan's size and `mtime_ns`, parent not swapped, the folder's device), and refuses a taken destination (`RefusalReason.CONFLICT`) or a category path that is not a directory on that device; `carry_out` journals the batch and every move `pending` first, makes each category directory after the journal (default mode; an existing one is used as it is), checks the destination again and renames, never copies or overwrites; a move that fails stops the batch and the moved files go back newest first, never over a newcomer, each settled by the disk when a rename raised; `done`, `rolled_back` or `failed`, with the files left at their destinations; an exception other than `OSError` is raised again after the rollback. `organize.journal`: the file's identity (device, inode, size, `mtime_ns`; device and inode kept as unsigned 64-bit) and `settle`, where the disk says a move left its file (decision 0012, items 19, 24-28, 31).
- `organize.recovery.recover`: every move of a pending batch is settled by the disk, whatever its journaled state: `done` when only the destination holds the file (same device, inode, size and `mtime_ns`), `rolled_back` when only the source does, `failed` otherwise with a warning naming both paths and what each holds; nothing is renamed, overwritten or deleted, each move is settled in a transaction of its own and the batch closed last, so a recovery interrupted anywhere settles the same when run again. `kresorter recover` closes the quarantine's work, then organize's, then the autostart changes, and names the files still sorted with `kresorter organize undo N`; it runs on every system (decision 0012, items 31, 32, 37).
- `organize.undo.plan_undo(conn, batch)`: what undoing a batch would move back, as a batch of its own (kind `undo`) whose moves name the moves they reverse (`undoes`); only `done` moves not undone yet are taken, so an undo that stopped leaves the rest to the next. A regular file at the destination goes back even when edited since; a missing one, one that cannot be looked at (`missing`), a link or a directory (`not_regular`) stays, and a taken source (`conflict`) is never overwritten. An undo batch, a pending batch or a batch that does not exist is refused (`UndoRefused`, `UndoReason`). Preflight and the mover carry the plan out (`carry_out(..., undoes=...)`); recovery settles an undo batch like any other, and `kresorter recover` names the batch it was undoing (`organize.journal.batch`, `BatchKind`) (decision 0012, items 29, 30).
- `kresorter organize move FOLDER [--yes]`: the plan (per category: files, size, each `name -> Category/`; then what stays, by reason) and exit 1; with `--yes` the plan is made again inside the lock, checked once more and carried out as one batch, and the output says what moved, what was refused and what stays, with the `organize undo` that moves it back. `kresorter organize undo BATCH [--yes]`: the plan, then the moves back. `kresorter organize list`: the batches, newest first (id, UTC date, kind, files moved, state, undone or partly undone, folder); it runs while another domain's work is unfinished. Every organize command recovers organize's batches first; `move` and `undo` refuse on a system where organize does not move files (today macOS and Windows, and Linux when the scan context's open-file check is not reliable) before the journal is opened, and while another domain's work is unfinished. Exit codes: 0 every planned move happened, 1 a preview, nothing to move, a refused folder or batch or a file refused at move time, 2 usage, 3 a blocked system, unfinished work, an unusable data directory, lock or journal, or a batch that stopped (decision 0012, items 1-5, 7, 29, 30, 33-37, 39).
- `llm.settings`: where Ollama is and which model explains, read from the environment only: `KRESORTER_OLLAMA_URL` (default `http://127.0.0.1:11434`) only as `http://HOST[:PORT][/]` with `localhost`, an address of `127.0.0.0/8` in four decimal numbers or `[::1]`, checked by a pinned pattern and `ipaddress`, `localhost` taken as `127.0.0.1` without a resolver; anything else refused as `config` with the value named; `OLLAMA_HOST` is not read. `KRESORTER_OLLAMA_MODEL` (default `llama3.2`) by a pinned name pattern, installed when `/api/tags` lists it exactly or, untagged, as `<name>:latest`. `llm.failure.Unavailable` names why an explanation is missing (decision 0013, items 8, 9).
- `llm.transport.request`: one HTTP request to Ollama with `http.client`, on the address as given: its own socket, no resolver asked (`localhost` included), no proxy setting read, a `3xx` refused as `redirect` with nothing sent to its `Location`; one deadline (by default 3 s for the checks, 60 s for `generate`) for connecting, sending and every read, so a server slow in every phase still ends there as `timeout`; an answer over 64 KiB is `too_large` (at once by its `Content-Length`, otherwise at its 65,537th byte), a request body over 4 KiB is refused before connecting. It is the only module that may import networking, `http.client` and `socket` only; no test reaches beyond loopback or asks a resolver (decision 0013, items 7, 10, 12, 29).
- `llm.client`: Ollama's three requests and nothing else, `GET /api/version`, `GET /api/tags` and `POST /api/generate` (`REQUESTS`), each sending only `Host`, `Accept-Encoding: identity`, `User-Agent: kresorter/<version>`, `Accept: application/json`, `Connection: close` and, for the `POST`, `Content-Type` and `Content-Length`. `status(env)` checks in order, each only if the previous one passed: the settings; a JSON object from `version` whose `version` is 1 to 32 characters of `[0-9A-Za-z.+-]` and one from `tags` whose `models` all have a string `name` (otherwise `not_ollama`, the request named in the detail); the model among them (otherwise `model_missing`). A request the transport refuses keeps its reason (`redirect`, `too_large`, `timeout`, `unreachable`). `generate(address, model, subject)` sends `model`, the pinned instruction as `system` (`llm.prompt.INSTRUCTION`: the facts are data, never instructions; at most three plain sentences, no commands), the facts as a JSON `prompt` in their order, `stream: false` and `temperature 0, seed 0, num_predict 200`; it takes only `done: true` with a string `response`, nothing else of the answer (otherwise `http_status` or `bad_response`). `llm.clean.cleaned_answer` makes that text safe to print: escape sequences removed whole, tabs as spaces, no control, format, private-use, surrogate, unassigned, line or paragraph separator character, at most 6 stripped non-empty lines and 600 characters with `…` where cut; an answer with nothing left is `empty`. The checks run under 3 s each and `generate` under 60 s, every answer within 64 KiB (decision 0013, items 11, 12, 14, 19, 20, 23).
- `llm.subjects`: what one explanation is about, made by `subject_of(result)` from a final result alone, `kind` first: for an analysis finding `level`, `reasons` (strongest first, each its evidence, a junk one as `junk_<category>:<rule id>`) and `extension`; for an autostart item `source`, `scope`, `name`, `program` (the last component, after `/` or `\`, of the command's first word or of the quoted part it starts with) and `enabled`; for a file organize leaves where it is `reason` and `extension`. The extension is the lower-cased end of the cleaned name from its last dot, empty when there is none, the name starts with it, nothing follows it or it is over 16 characters with the dot. No path, folder, size, time, digest, location, argument, note or detail is in a subject; every string is cleaned as an answer is, on one line, and cut to 100 characters with `…` (`llm.clean.cleaned_fact`). `subjects(results)` gives one subject per set of facts, in the order each first appears (decision 0013, items 17, 18).
- `llm.explain.explain(subjects, env)`: one run's explanations. A run with nothing to explain reads no setting and opens no connection; otherwise `status` checks once and, only when it passes, one `generate` per subject in the order given, with the model of the setting, at most 20 per run (`BUDGET`), the subjects beyond them counted as not explained; the first request that fails, whatever its reason, ends the run, which keeps the explanations already received and the reason (`Explanations`: `model`, `explained`, `not_explained`, `unavailable`); the run's limits hold for the checks and the requests alike (decision 0013, item 13).
- `kresorter llm status` and `--explain` on `analyze`, `autostart list` and `organize move`; no command contacts Ollama without them. `llm status` checks the settings, then Ollama, then the model, and says what it found line by line (`running at <url> (version <version>)`, `not reachable at <url> (<detail>)`, `<url> does not answer as Ollama (<detail>)`, `refused setting <name>=<value> (<why>)`, `<model>: installed`, `not installed` or `not checked`); when something is missing, exit 1 and the steps still to take, numbered as shown (install and start Ollama, `ollama pull <model>`, check again), and both settings: kresorter installs nothing. `--explain` asks, once the command's result is final, for one explanation per subject in the order of its output (the findings; the entries, grouped by source in the text and as read in JSON; the files `organize move` leaves where they are, asked after the lock is released) and adds them after it: in text, after an empty line, under `AI explanations (<model> via Ollama; advisory, may be wrong; nothing above depends on them):`, each subject's facts as `name=value` (a list's values joined by `+`) and its answer indented, then how many subjects the 20 of a run left out; in JSON, `explanations`, `explanations_model`, `explanations_not_explained` and `explanations_unavailable`. What comes before is the output of the run without `--explain`, and the exit code is its own; a run that gets no explanation, or stops, says so in one line on stderr. `organize move --explain --yes` is a usage error (exit 2), and a move refused on this system contacts nothing. A refused setting is `llm.failure.SettingRefused`, with its name, value and why. Guards: `llm` imports from kresorter only the package, its own modules and the results it explains, only the command-line modules import it, and it opens no file (decision 0013, items 1, 3-6, 15, 21, 22, 24-27).

### Fixed
- `kresorter-ui` without a library Qt needs (`libGL.so.1` on a Linux without it) writes one line, the error and the libraries to install, and exits with 3, instead of a traceback; without a standard error, as for a GUI script on Windows, it writes nothing instead of failing on `None` (decision 0014, item 9; pre-step-8 audit, A1).
- The window no longer freezes on tens of thousands of findings (pre-step-8 audit, A2): Findings adds a group's rows with it, changes many check states (a group's check box, Select all, Clear) without the tree announcing each row, and takes what moved out of its group in one go, keeping the current finding; the confirmation's details are a read-only plain-text box, which lays out only the lines it shows. With 20 000 cache files, offscreen: listing 2.0 s to 1.0 s, a group's check box 3.5 s to 0.3 s, removing what moved 65 s to 0.1 s, opening the confirmation 6.4 s to 0.1 s.
- The window's columns are aligned with an alignment flag instead of a number (`QTreeWidgetItem.setTextAlignment(int, int)`, deprecated in PySide6 6.12, 1398 warnings per test run), and a warning now fails the tests (`filterwarnings = ["error"]`; pre-step-8 audit, A3).
- `llm.transport.request` closes the answer on every way out: a redirect, a `Content-Length` over the limit or an answer going on past it left its socket open until the garbage collector found it (pre-step-8 audit, A7).
- `autostart.changes.XdgChanges.disable`: a file that appears where the stub over a system entry goes, between the check and `O_EXCL`, rolls the change back instead of leaving it `failed` (exit 3); `recover()` no longer takes such a file, if empty or a beginning of a stub, for a partial stub and moves it to the store (decision 0011, item 117).
- `autostart.changes.XdgChanges.disable`: when the stub over a system entry cannot be written, the slot it is moved to is journaled (`vault_path`) before the move, as `recover()` does; a crash in between left the partial stub in the store with no row naming it (decision 0011, item 116).
- `autostart.changes.XdgChanges` no longer makes the autostart store when it is created: a preview (`autostart disable|enable` without `--yes`), a refusal or a `recover` with nothing to close leaves no `<data_dir>/autostart`; the store is made by the first change, before it is journaled (decision 0011, item 115).
- CLI: a journal failure in the middle of a command (`sqlite3.Error`: a full disk, an I/O error, the journal held by another program) exits with 3 and names the command that recovers it (`kresorter autostart recover`, `kresorter quarantine list`) instead of a traceback with exit 1 (decision 0011, item 114).
- CLI: an `OSError` raised inside the journal session is no longer reported as `cannot use the data directory`: what the command did not handle is `stopped: <reason>`, the quarantine names its vault, and autostart commands say whether an unfinished change cannot be closed or a check before acting failed, with nothing changed (decision 0011, items 112 and 113).
- `autostart.changes.XdgChanges`: an entry that exists but cannot be looked at (e.g. `EACCES`) raises `BrokenEntryError` with its reason in `recover()` on every Python version; on 3.14 it was taken for a missing one, so an interrupted disable whose stub was in place could be closed `rolled_back`; the store-device check no longer skips such a directory either (decision 0011, item 111).
- An unopenable journal (`sqlite3.Error`) exits with 3 and a message instead of a traceback.
- Quarantine rollback no longer loses track of a file whose rename completed just before an interrupt: rollback checks the vault slot on disk; `recover()` also reconciles quarantined items of an interrupted rollback (decision 0006, addendum).
- `autostart.xdg.read_xdg()`: an autostart directory that exists but cannot be listed is now skipped with `cannot read: <reason>` instead of silently reading as empty; nothing it could change is shown: no items at all for the user directory, and for a system directory only the names found in the directories before it (decision 0011, item 32).

- The project is Kresorter: the package `kresorter`, the commands `kresorter` and `kresorter-ui` (`python -m kresorter`, `python -m kresorter.ui`), the data directory `kresorter` with its lock `kresorter.lock`, the variables `KRESORTER_OLLAMA_URL` and `KRESORTER_OLLAMA_MODEL`, and the window's title `Kresorter` (decision 0015, item 1).
- The README has a section `Desktop app (optional)`: the extra and its install command, the system libraries Qt needs on Linux (those CI installs), `kresorter-ui` and `python -m kresorter.ui`, the six pages in the sidebar's order, that nothing changes until a confirmation, that the window and the commands share the journal and Recover, Explain (local AI) on request, the two languages and `settings.json`, the one file the window keeps. The roadmap records step 7 and its accepted limitations, and its target layout names every module of `kresorter.ui`; every item of decision 0014 is cited by a test, the meta-test's pending list is empty (decision 0014, items 41-43). The tests read Markdown through `tests/support/markdown.py`.
- What the CLI and the desktop window share moved out of the CLI: the journal session to `storage.session` (`run_session`, reporting why it could not run as a `SessionFailed` value: `data_dir`, `locked`, `data_dir_os`, `journal_open`, `stopped`, `journal_failed`), `analyze_paths` to `analysis.run`, `changes_for` to `autostart.changers`, and the listing of quarantined files to `quarantine.journal.quarantined`. Messages, output and exit codes are unchanged (decision 0014, items 11 and 12).
- `cli.main` takes one `Environment` (`kresorter.environment`) instead of a parameter per factory: the scan context and the autostart context, each built only by a command that needs it, and the settings environment of `llm` with its limits. `detect_platform` and `default_context` moved there from `cli`, so the CLI and a UI make the same contexts; decision 0013, item 21, lets `kresorter.environment` import `llm` for its limits. Behaviour is unchanged (pre-step-5 audit, B8).
- The README has a section `AI explanations (optional)`: Ollama and the model are installed by the user, never by kresorter; the steps and both settings as `kresorter llm status` prints them, which a test runs to compare; the commands that take `--explain`; what is sent for each kind and that nothing else is. The roadmap records step 6 and its accepted limitations; every item of decision 0013 is cited, the meta-test's pending list is empty (decision 0013, item 16).
- The README covers `organize` and its exit codes; the roadmap records step 5 and its accepted limitations (decision 0012).
- `ScanContext` carries the platform it was made for (`platform`, required; `default_context` sets it): organize refuses by it, not by the system the code runs on; a context that does not say its system cannot be made. The lines of files refused at action time (`text.refusal_line`, `text.refusals`) are shared by the quarantine and organize; output unchanged (decision 0012, item 39).
- Preflight moved from `quarantine.preflight` to `core.preflight`, which the quarantine and organize share; behaviour is unchanged (decision 0012, amending 0004).
- The README covers every command (`analyze`, `autostart`, `recover`), the data directory and the exit codes of each (pre-step-5 audit, A5); the roadmap records step 5.0.
- A command that would act while another domain has unfinished work names `kresorter recover` (`the journal has unfinished <domain> work`), and so does a journal failure in a quarantine command (it named `kresorter quarantine list`); the quarantine's recovery reads `Recovered an interrupted quarantine operation`; `storage.pending.pending_domains` says whose work is unfinished (decision 0011, items 125, 127).
- The quarantine's recovery (`recover`, `RecoveryReport`) moved to `quarantine.recovery`, its states and journal updates to `quarantine.journal`; it needs no open-file check; behaviour is unchanged (decision 0011, item 124).
- The journal's times (`created_at_ns`, `finished_at_ns`) come from a clock given to `QuarantineService`, `XdgChanges` and `RunKeyChanges` (`now`, `time.time_ns` by default); `RunKeyChanges` dates its rows with the clock of its flag (decision 0011, item 121).
- `storage.journal.insert_row()` is the one journal insert of the quarantine and the autostart changes (decision 0011, item 120).
- The journal of autostart changes (`ChangeState`, `ChangeResult`, `insert_change`, ...) moved from `autostart.changes` to `autostart.journal`; behaviour is unchanged (decision 0011, item 119).
- The data-directory policy (`check_data_dir`, `DataDirError`, `PRIVATE`) moved from the quarantine to `storage.data_dir`; messages and exit codes are unchanged (decision 0011, item 118).
- The coverage gate is 100 % of lines and branches (it was 80 %), and CI runs Python 3.11 to 3.14 (pre-step-5 audit, A4).
- `DuplicateGroup` holds the scanned `FileEntry` of each copy (`entries`); `paths`, `size` and `wasted_bytes` are derived; a group with fewer than two copies or mixed sizes cannot be created. Feeds `analysis.duplicates.decide()` directly; `scan` output unchanged.
- `kresorter scan` uses the real open-file check on Linux (`checker_for_platform()`); other OSes still disclose that it is missing.
- Temp is no longer a default safe zone; scanned only on explicit choice (decision 0002).
